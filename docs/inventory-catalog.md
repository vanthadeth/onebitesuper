# Inventory catalog — milestone 1

This historical milestone is extended by [Unified item catalog](unified-item-catalog.md), which replaces separate catalog identities with independent type, category and sale eligibility.

Inventory is a separately installable app at `/onebitesuper/inventory/`. Run locally with `npm run dev:inventory` (port 5175). Root build, Pages build, preview and browser checks include it.

## Included

- Materials: ingredient/packaging category, pieces/grams/millilitres, optional named request pack and explicit base-unit quantity.
- Sellable items: separate records, free-text category, selling unit and whole-KHR master price. No hardcoded menu or sample records.
- Photos (JPG/PNG/WebP converted to JPEG), optional English name, descriptions and active state. Active by default; only shown on edit.
- Search, category and Active/Inactive/All filters, default Active; compact shared headings, cards, bento Hub, five equal mobile navigation items.
- Shared username/PIN login and remembered seven-day session. Only Owner needs authenticator verification. Inventory module access is configurable in Admin Roles. Owner gets the new module/action grant; existing staff grants are preserved. Catalog authoring remains strictly Owner-only.

## Server boundaries

`20261010122414_inventory_catalog.sql` installs the catalog, immutable operation receipts and guarded `onebite_inventory_api`. Public and Supabase authenticated clients have neither table nor RPC privileges. RLS is enabled with no client policies intentionally: the custom-session Edge Function is the only route. Every request checks the existing session guard and current module grants. Authoring checks both the real Owner role and the catalog action; Owner MFA remains valid for seven days within the fixed session lifetime.

`inventory-access` validates the publishable key, opaque token, body limit and allowed origin. It generates operation fingerprints itself. Catalog photos are in the private `catalog-photos` bucket; photo reads must refer to an attached, authorized catalog record. Uploads decode/re-encode JPEG server-side. An operation's photo cannot be overwritten by a changed retry. The function uses `verify_jwt=false` because internal opaque sessions are verified explicitly rather than using Supabase Auth JWTs.

## Offline behavior

The separate Inventory SQLite database is persisted in IndexedDB. A token-encrypted cached catalog authorizes offline access for up to 24 hours and never beyond session expiry. Actor-scoped outbox entries use non-extractable device keys in IndexedDB so sign-out and re-login do not erase unpublished work; another account cannot publish the previous actor's operations.

Each queued edit has a stable operation UUID and the original expected item revision. The server commits the item, receipt and audit event in one transaction. A lost response can be retried without double-writing. Local values remain marked Pending sync until acknowledged. A competing edit becomes Needs review rather than overwriting the newer record. The saved copy remains viewable; staff can explicitly discard a queued copy and edit the latest record. Base units are locked after creation in this first build to prevent future quantities from being reinterpreted. There is one queued edit per item at a time.

Automatic reconnect attempts complement online/focus events. Ordinary transient failures keep the operation queued; session revocation or missing permissions stop publishing. Clearing browser site data or uninstalling without retaining storage can remove unpublished edits; publish pending changes before clearing storage. Photo requests do not use public URLs or service-worker API caching.

## Following steps

Recipes and selectable sauces, site availability exclusions and price overrides, then stockroom/site requests and independently counted dispatch/receipt. No stock balance, request, batch-yield conversion, recipe deduction or POS consumption is implemented in this catalog milestone. The master price/all-sites availability is the inherited default; POS integration follows recipe implementation.

## Verification

`npm test` covers domain and Edge request boundaries. `supabase/inventory-catalog.verify.sql` tests authorization, idempotent retries, changed-payload retries, stale revisions, unit protection, photo access, grant revocation and recent Owner verification in a rollback-only transaction. GitHub's isolated Postgres job runs it. `tests/inventory.spec.ts` exercises catalog creation, filters, offline reload/reconnect, conflicting edits, staff visibility, keypad sign-in and offline photos on phone/desktop. Pages checks verify independent install scopes and reject unauthenticated live catalog requests.

The Supabase CLI download could not start in this environment. The migration file uses the actual version generated by Supabase's successful `apply_migration` operation, rather than an invented local version.

## Recipe composition

Finished products are reusable recipes, not independently stocked prepared goods. Open **Hub → Finished products** on mobile (or Finished products in the desktop sidebar). Add raw materials in their own base units, with quantities for one finished-product unit. Finished products have no selling price. Their base unit is locked after creation.

Sellable items can contain finished products and raw materials/packaging. **Create sellable item** in a finished-product detail starts an item with that product already included; adjust quantities, selling unit and master price. The recipe editor and detail show the combined raw-material breakdown for one unit. There is no automatic g/kg or ml/L conversion: enter amounts in the unit shown.

Owner-only authoring, active-by-default creation, confirmation for active changes, private photos, revision conflicts and 24-hour offline authorization remain in force. Recipe quantities must be positive with at most three decimal places; pieces must be whole numbers. Duplicate, missing, inactive, self-referencing and sellable-as-component lines are rejected. Finished products contain raw materials only, so cycles cannot form. Up to 100 components are supported.

Recipe edits use the existing encrypted SQLite outbox. Materials sync before finished products, then sellable items. The backend saves an item and recipe in one transaction, with an immutable operation receipt; older clients omitting the recipe preserve its value. Existing records are retained with empty recipes. No example ingredients/products are inserted.

This builds catalog recipes and their raw-material calculation. POS sale posting, automatic stock deduction, stock balances and batch-yield recording remain later milestones; editing a recipe does not move inventory.
