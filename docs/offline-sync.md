# Supabase and SQLite

Supabase is the authority for real users, grants, sites, settings and activity. The apps no longer offer local demo identities, catalog items, invoices or payments. Browser startup removes only the old OneBite preview storage keys. Existing Supabase records and audit history are preserved. Test fixtures live under `tests/fixtures` and are not imported by production entrypoints.

Admin uses the shared `@onebite/offline` package. The pinned sql.js WASM engine runs SQLite in the browser; IndexedDB persists the SQLite database file. This works without cross-origin isolation, OPFS or SharedArrayBuffer requirements, including GitHub Pages and supported Safari browsers. The WASM asset is bundled locally and precached by the app service worker. CSP permits WASM compilation with `wasm-unsafe-eval`; it still denies JavaScript eval and third-party scripts.

After an authenticated Supabase response, Admin stores an AES-GCM-encrypted snapshot keyed to that opaque session. The SQLite file contains a hash of the session identity, encrypted business data and the verification time; it does not contain the token, PIN, authenticator secret or recovery codes. The opaque token remains in the remembered-session storage introduced previously. Encryption reduces accidental disclosure of exported files; it does not protect against active same-origin JavaScript compromise.

On network failure, `me` can restore only a matching, previously authorized snapshot verified within ten minutes. Admin clearly labels this data as offline/read-only. There is no offline PIN login or permission mutation, and no queued Admin writes. A hard offline authorization deadline and the existing inactivity/session limits remove access when expired. Logout/revocation clear the remembered session and delete the SQLite file. If storage is unavailable, live requests still work and the app reports that offline caching is unavailable.

The sync button and browser reconnect event validate the session with Supabase and replace the cached snapshot with the current authorized response. Offline mode cannot certify server-side revocation until reconnect; its ten-minute deadline bounds that exposure. Photographs are not copied into the SQLite snapshot; offline site details remain available, but remote photos may be unavailable. Activity shows the snapshot's recent logs; loading additional server pages requires connectivity.

POS now has a clean setup screen. Its previous browser-only sales prototype was removed. A production catalog, shifts, order ledger and offline write/sync protocol are not yet implemented. That milestone needs durable per-site SQLite order/outbox tables, idempotent server writes, device/site ownership, allowance reservation/conflict rules, and reconciliation. Do not enable real sales until that path is implemented and tested.
